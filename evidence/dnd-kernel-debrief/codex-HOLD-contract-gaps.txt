**Blocking findings**

1. **The contract cannot yet demonstrate the four required integrations.**

   In [§2.2](/Users/daniel/Developer/Rottay/r4-recon-opus/evidence/dnd-kernel-debrief/index.md:224), `getTargetProps()` receives no target identity or target-specific resolver. The sole `resolveTarget(event, payload)` must somehow recover a view key, column key, Tree key, or Kanban `{columnId, position}`. Current implementations bind those values through closures. The proposal supplies neither that binding nor a declared DOM registration mechanism.

   Likewise, a generic `TTarget` supplies no equality/projection rule for target stamps. Existing anatomy differs: `data-drag-target`, `data-drop-target`, `data-drop-before`, `data-dropping`, and Tree’s absent-versus-false attributes.

   Require concrete typed adapter examples for all four owners, including ColumnMenu’s separate handle/row and Kanban’s nested card/column targets. Specify target identity, stamp ownership, propagation, drop-time validation, callback order and exactly-once termination. Matching handler names does not settle these contracts.

2. **The promised keyboard and pointer abstractions are absent from the API.**

   `UseDragSessionOptions` has no keyboard mode, announcement callback, keyboard target resolver, focus registration, preview/rollback operation or imperative move entrypoint. `SortableAnnouncements` is declared separately without being connected to anything.

   The claimed event-generic core explicitly takes `React.DragEvent`, always returns HTML5 source props, and mandates `dataTransfer`. That is an HTML5 adapter, not the generic session core described in §2.8.

   The keyboard contract must distinguish candidate movement from committed movement. Otherwise “one commit point,” immediate Kanban moves, and grab-mode Escape restoration cannot be audited. Also define invalid axis combinations and the treatment of `Home`/`End`, which `resolveNavigationIntent` returns but `MoveIntent` cannot represent.

3. **Press cancellation and handler composition conflict with the stated invariants.**

   `useInteractionState` holds state **per hook instance**. The proposed source-prop factory receives no reference to the existing instance. Creating another instance cannot clear the pressed state owned by ColumnMenu’s row or its Button.

   Moreover, [composeHandlers](/Users/daniel/Developer/Rottay/r4-recon-opus/packages/core/src/foundation/behavior/runtime/compose-handlers/index.ts:21) deliberately skips its second handler when the first prevents default. I executed that helper directly: after the first handler called `preventDefault()`, the second ran **zero times**.

   This matters particularly for Upload: its current order is `preventDefault` → disabled guard → clear hover → public `onDrop(event)` → process files. Internal processing continues despite the already-prevented event. Blindly applying the proposed composition law changes that behavior.

   Define explicit access to the owning press state and distinguish vetoable actions from mandatory cleanup. Preserve Upload’s raw-event callback and ordering. An unconditional cleanup promise cannot rely on a chain that intentionally skips handlers.

4. **Placement is reasonable, but the declared write set cannot satisfy the current gate.**

   The foundation dependency concern is valid: its inspected production imports are React/local, while roving-focus imports the i18n runtime. Existing primitive and structure consumers support the proposed tier.

   However, the [structure gate’s collection dependency ranks](/Users/daniel/Developer/Rottay/r4-recon-opus/packages/core/scripts/check/architecture/audits/structure/index.mjs:173) name `combobox`, `roving-focus`, `typeahead` and `listbox`—not `sortable`. Under the current dependency rules, the proposed `sortable → roving-focus` edge falls through to `sibling-owner-dependency`.

   Add the narrow structural admission and its tests to the singleton write set. Do not widen the baseline. “Beside an admitted kernel” does not itself admit a new dependent owner.

5. **The executable acceptance promises exceed what the named instruments measure.**

   - N1 is listed under a unit suite, but `fireEvent.drop()` dispatches the requested event independently of browser drag negotiation. Assert dragover cancellation in a unit test; use an actual browser drag to prove the browser-level claim. The [HTML specification](https://html.spec.whatwg.org/multipage/dnd.html#drag-and-drop-processing-model) distinguishes that processing model from manually dispatching events.
   - Require each mutation to fail **at least its designated test**, not “exactly one.” Additional legitimate failures are not instrument defects.
   - R5 proposes adding `0.1h/0.5h/0.9h` cases that [already exist](/Users/daniel/Developer/Rottay/r4-recon-opus/packages/core/src/components/primitives/display/tree/tests/Tree.modern-engine-advanced.test.tsx:206). Add actual quarter-boundary cases, including equality at 25% and 75%.
   - Add cancellation after leaving all targets, disable/removal during a session, unrelated external drags, nested-target single commitment, and caller-prevented-event cases.
   - Use immutable base/candidate SHAs for the changeset receipt. `--base=main` can compare main with itself after integration; the repository’s [gate manifest explicitly warns about that](/Users/daniel/Developer/Rottay/r4-recon-opus/packages/core/scripts/check/automation/gates/manifest/index.mjs:54).
   - Public hook retirement needs the authorized API decision, appropriate release declaration, consumer documentation and complete export/type removal accounting. Zero local callers plus a passing changeset check is insufficient authorization.

**Other corrections**

The rejection of third-party libraries on dependency policy is coherent. The claimed measured DOM incompatibility is not: dnd-kit explicitly supports augmenting existing elements without additional wrapper nodes. Retain the policy argument; remove the unsupported inevitability claim. [Official project documentation](https://github.com/clauderic/dnd-kit#readme)

“Reading `dataTransfer` during dragover is forbidden” is too broad. Payload contents are unavailable in protected mode; formats and kinds remain enumerable. That distinction matters to rejecting non-file drags in a file-drop adapter. [HTML drag data store](https://html.spec.whatwg.org/multipage/dnd.html#the-drag-data-store)

The duplicate `normalizeDraftOrder` observation is stale after `8c96f4197`. Also fix §3.3’s incorrect invariant references and replace invariant 6’s impossible “no quoted English word” grep: legitimate protocol literals include `'move'`, `'before'` and `'blocked'`.

**Appendix A answers**

1. **Q1 — Placement:** Accept `components/primitives/runtime/collection/sortable/` in principle, with explicit admission as a downstream consumer of roving-focus and a tested reverse-edge prohibition. Include that gate change in the write set. Keep public exposure separate; this placement does not imply a new root export.

2. **Q2 — FAM-13:** Prefer **B for this bounded contract**. Permit FAM-13 to consume applicable resolvers; do not claim this HTML5 interface already accommodates its pointer lifecycle. WidgetBoard has activation thresholds, pointer identity, preview state, origin restoration and live ownership checks that an event type parameter does not solve. Reconcile this narrower commitment explicitly with the handoff. If full session adoption remains mandatory, return a concrete event-neutral lifecycle contract for joint review before adopting A.

3. **Q3 — Tree keyboard movement:** Prefer an explicit, keyboard- and touch-operable **Move affordance** that selects a destination and before/inside/after position. Preserve bare arrows, Space and Enter for existing Tree navigation/selection. Specify invalid self/descendant targets, cancellation, announcements and focus restoration. A modifier shortcut may supplement this; it should not be the sole discoverability mechanism. This blocks the operability lot, not a properly isolated transport extraction.

4. **Q4 — Live region:** Confirm consumer-owned regions and kernel-emitted events. Make those events generic over the actual payload/target and connect them to the API. Preserve Kanban’s timing during transport adoption. Test repeated identical outcomes, especially consecutive blocked moves. `useAriaAnnounce` retirement or repair is a separate decision; its orphan status does not justify changing Kanban here.

5. **Q5 — File drop:** Keep it in this WO as a separately named capability. Remove `accept`/`multiple` from its options if it does not enforce them. Define raw-event callback ordering, disabled behavior, file identification, containment and cleanup. Preserve each consumer’s picker and keyboard fallback. “No accessibility surface” is too strong for an adapter attached to Upload’s accessible drop control.

6. **Q6 — Transport/operability split:** Confirm the split. Transport lots preserve existing behavior; additions and defect repairs are declared separately. Correct ColumnMenu’s premise and preserve its existing move buttons. SavedViews’ grab behavior must not steal Space/Enter from its selection, rename or menu controls. A press-latch repair cannot simultaneously be represented as byte-identical behavior.

7. **Q7 — Mechanization:** Require a bounded instrument before closing the DnD consolidation criterion. Extend existing machinery. Verify actual imports/adoption and detect independent transport state/handler implementations; do not merely forbid names matching `handle*Drag*`. Adapter callbacks legitimately remain. Drill renamed/inline handlers and newly added files, with explicit frozen-engine exclusions. This establishes DnD consolidation only; F-69’s geometry/export obligations remain separately accountable.
