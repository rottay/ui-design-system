# Round R7 — customization depth, tenant distinctiveness and catalog parity

R7 is the owner-authorized post-certification round of `WO-CRA-23`. It begins
only after R6 has a local Codex-accepted frozen-tree result. R7 does not weaken,
replace or retrospectively re-score R0-R6. It uses that certified tree as its
immutable baseline and proves that Modern is not merely broad, but deeply and
coherently customizable across the complete 252-family inventory.

## Outcome

One canonical Modern component system can produce clearly different products
without tenant selectors, tenant-conditional TSX, copied component libraries,
a second compiler or a second engine. Standard controls remain few and
high-leverage, Pro remains curated around product-comprehensible capabilities,
and Expert remains an exact bounded escape hatch. Tenant distinction must be
visible beyond palette through coherent typography, geometry, edge, material,
depth, density, rhythm, icon posture, motion, motif, navigation, responsive
composition and recipe/anatomy decisions.

R7 is complete only when every one of the 252 families has a reproducible
customization disposition and every eligible family has observed causal reach
from the canonical static `BrandTheme` and DB `TenantTheme` paths to a stable
DOM part and an observable property. A family that is intentionally invariant
must prove why customization would damage semantics, accessibility or product
coherence; silence is not an invariant.

## Relationship to external systems

Public systems are non-normative benchmarks. They are used to discover proven
ideas, failure modes and missing capabilities; they do not supply Rottay names,
visual identity or architectural authority.

| Reference | Idea to study | Rottay disposition |
|---|---|---|
| [Adobe Spectrum CSS](https://opensource.adobe.com/spectrum-css/) | base/theme/context separation and component modifier fallbacks | Compare with the existing foundation/semantic/recipe/family-private pipeline; adopt only missing semantics through current authorities. |
| [PatternFly design tokens](https://www.patternfly.org/foundations-and-styles/design-tokens/overview/) | explicit scope/component/property/concept/variant/state taxonomy | Test whether current names are unambiguous; keep an existing Rottay name when it already owns the same semantic decision. |
| [Material Web](https://material-web.dev/theming/material-theming/) | reference to system to component token layering | Use as a sanity check for alias direction and fallback ownership, never as a reason to mirror Material names or visual grammar. |
| [React Aria Components](https://react-spectrum.adobe.com/react-aria/components.html) | accessible behavior, public parts, slots and state data attributes | Use as a behavioral and anatomy oracle for equivalent families; do not copy its styling or replace a correct Rottay component. |
| [Base UI](https://base-ui.com/react/overview/about) | open headless composition, focus/keyboard behavior and direct part access | Use for capability-gap and edge-case review; dependency adoption requires a separately approved gap decision. |
| [DTCG 2025.10](https://www.designtokens.org/TR/2025.10/format/) | portable typed token interchange, aliases and composite values | Provide a deterministic non-authoritative interchange projection if useful; the production compiler and contracts remain canonical. |

For every benchmarked idea, the R7 benchmark matrix records: source and
version/date; the problem it solves; equivalent local family or authority;
local behavior and naming; delta; accessibility, SSR, RTL and responsive
consequences; license if source reuse is proposed; and one disposition:

- `ALREADY_EQUIVALENT`
- `ADOPT_IDEA_IN_EXISTING_AUTHORITY`
- `IMPROVE_EXISTING_FAMILY`
- `PROPOSE_NEW_CAPABILITY`
- `PROPOSE_NEW_FAMILY_FOLLOW_ON`
- `REJECT_INCOMPATIBLE`

The executor pins the exact page or repository revision and access date used by
each comparison. A future upstream change cannot silently alter an accepted R7
disposition; updating a benchmark requires a new source digest and re-audit of
only the affected rows.

Names and source code are never copied merely to claim parity. A new family is
outside the fixed 252 denominator and therefore requires a separate
owner-approved work order after the R7 gap census. R7 may improve existing
families and may prepare a bounded proposal, but it may not silently change the
inventory denominator.

## Binding starting authorities

- `family-inventory.json`: exact 252-family baseline.
- `customization-model.json`: Standard/Pro/Expert tiers, 12 art-direction
  groups, 14 target recipe groups, propagation KPIs and proposal law.
- `tenant-art-direction.json`: same-tree BitHire and The Management directions.
- `quality-rubric.json`: eligibility, craft floors, stress matrix and CSS
  ownership.
- `visual-craft-contract.json`: failure taxonomy, visual vetoes and checkpoint
  policy.
- `evidence-contract.json`: fresh source-bound receipts and round artifacts.
- Generated live census, control, hook, theme and prototype authorities named
  by `README.md`; copied counts in a report never override them.

At R7 entry, regenerate the customization census and record the source digest.
The previously observed 7,474-name universe, 2,691 unadjudicated reads and 276
dead writers are planning context only. R7 uses the fresh generated numbers and
does not preserve a stale count as a target.

## Non-goals and fences

- No wholesale import or visual port of Spectrum, PatternFly, Material, Radix,
  React Aria, Base UI, Web Awesome, Open Props, Chakra or another library.
- No second engine, compiler, token authority, icon supplier or component tree.
- No tenant selector, tenant ID in CSS, tenant conditional in TSX or app-owned
  patch to DS-private anatomy.
- No unbounded `--ds-*` namespace and no public token created to improve a
  coverage number.
- No duplicate component or alias when a canonical Rottay family already owns
  the capability.
- No mutation of published profile IDs. Version a genuinely new profile and
  preserve the old meaning and migration path.
- No color-only tenant proof, no screenshot-only causality and no token-only
  family completion.
- No baseline or pin re-anchoring, test weakening, generated-output hand edits
  or acceptance by the writer.
- Classic and Rustic remain read-only except a separately proven minimal
  compatibility consequence of a shared public contract.
- R7 does not publish or push. Codex may create local audited commits only.

## Execution waves

### R7.0 — frozen baseline and benchmark matrix

This wave is read-only except for R7 evidence and governed contract fixes.

1. Verify R6 accepted HEAD, clean index and exact inherited worktree ownership.
2. Regenerate the token/control/customization census once and hash it.
3. Resolve the 252 families to public exports, source owners, stable DOM parts,
   applicable states and current customization groups.
4. Compare the local catalog against the external references above by
   capability, behavior and anatomy, not by component name count.
5. Produce a gap matrix with one explicit disposition per external idea.
6. Reject proposals whose only benefit is another name, another raw token or a
   visual imitation of a reference system.
7. Generalize `quality-evidence/v2/seal-round.mjs` before the first R7 seal: its
   summary outcomes, KPIs and capture counts must derive from the selected
   round artifacts rather than the current R0-only constants. Add negative
   drills proving an R7 seal cannot emit R0 notes, zero captures or fabricated
   family outcomes.
8. Freeze the accepted R7 conflict graph and shared-authority requests.

Exit: 252/252 families mapped; benchmark ideas fully adjudicated; zero implicit
inventory additions; exact live debt baseline; no productive family writes.

### R7.1 — token and CSS ownership closure

1. Classify every Modern-reachable custom-property writer and read as
   foundation, semantic, group recipe, family-private, bounded Expert,
   compatibility with owner/expiry, or dead with death proof.
2. Resolve every unadjudicated read to one canonical writer/fallback or remove
   it with consumer evidence.
3. Remove dead writers only after source/generated reconciliation, successor
   adjudication and a negative drill proving the removed path is unreachable.
4. Prove alias direction is acyclic and flows from reference/foundation toward
   semantic, recipe and family-private consumers.
5. Keep family-private implementation variables private. Promotion requires a
   stable part, declared type/bounds, two plausible tenant values, productive
   consumers, static/DB parity and exact restore.
6. Generate a DTCG-compatible interchange projection only if it is lossless for
   the supported types and aliases. It is an output, never a second source.
7. Record CSS output size, compiler time, runtime application time and first
   paint against the R6 baseline; R7 may not buy customization with an
   unexplained performance regression.

Exit: zero dead or unowned Modern-reachable CSS; zero targeted unadjudicated
reads; zero alias cycles; zero generated-only remnants; deterministic source to
artifact output; no dormant public channel.

### R7.2 — family anatomy and state contracts

For every family, create or generate one machine-readable disposition with:

- canonical family ID, layer, source owner and public exports;
- root and stable parts/slots, including the honest absence of a root;
- states and state attributes/pseudo-classes;
- property groups affected by customization;
- eligible art-direction axes and invariant axes with reasons;
- semantic, recipe, family-private and Expert inputs;
- exact fallback chain and restore digest;
- static and DB causal probes;
- responsive/container/mobile behavior;
- EN/ES/AR-RTL and large-text consequences;
- keyboard, focus, pointer, forced-colors, reduced-motion and
  reduced-transparency requirements;
- SSR/hydration/portal requirements where applicable;
- external behavior/anatomy comparisons and disposition.

Changing DOM anatomy requires an observable product, accessibility or
resilience defect. R7 does not churn markup merely to resemble an external
library. State hooks must describe semantics (`open`, `selected`, `invalid`,
`pressed`, placement, drag state, and similar) rather than tenant identity.

Exit: 252/252 dispositions; every eligible part/property edge has one owner;
every invariant is justified; zero unknown root/part/state ownership.

### R7.3 — recipe-group expansion from six to fourteen

The existing groups are reconciled into the target semantic groups in
`customization-model.json`: control, field, choice, card, sectionCard, metric,
dataTable, chart, navigation, overlay, feedback, form, collection and shell.

For each group:

1. Prove at least two productive families share the decision and at least two
   plausible tenant postures need different values.
2. Define a closed set of axes and values; do not expose an arbitrary CSS bag.
3. Map each value to anatomy, emphasis and observable property groups.
4. Preserve the current default through the fallback chain.
5. Prove static/DB equivalent normalized output and exact restore.
6. Calibrate three representative families before propagating.
7. Propagate only through disjoint family cohorts of at most 25.
8. Measure coverage, leverage, depth and resilience; a recipe that moves one
   cosmetic property or one family is rejected or kept private.
9. Exercise every recipe across density, rhythm, type-scale, mode, responsive,
   RTL, forced-colors and reduced-motion intersections that apply.
10. Reconcile obsolete group names without breaking published profile IDs.

Exit: 14/14 target groups are productive and source-bound; every admitted group
satisfies the two-family/two-posture law; coverage, resilience, canon closure
and path parity equal 1; unknown targeted impact equals 0.

### R7.4 — coherent art-direction postures

Build five non-product reference postures through the existing profile and
recipe registries. The descriptive postures are test fixtures, not required
public IDs:

1. operational/technical;
2. editorial/premium;
3. consumer/soft;
4. institutional/dense;
5. expressive/event.

Each posture must make a coherent decision in all applicable groups:
palette/ink, typography, geometry/silhouette, edge/divider,
material/depth, density/rhythm, icon posture, motion cadence,
background motif, navigation chrome, responsive composition and
recipe/anatomy. `none` or inherited is allowed only with a product reason and
must not create accidental holes.

All five render the same deterministic DS tree and content. For every pair of
postures, evidence must show distinction on at least eight observable axes and
at least six non-color axes, remain recognizable in grayscale and after primary
hue neutralization, and preserve identical semantics and task completion.
Color, logo and copy do not count toward the six non-color axes.

BitHire and The Management remain the binding first-party canaries and must not
regress. Reference postures do not authorize new tenant-specific source.

Exit: five coherent postures; ten pairwise comparisons; BitHire/TMM regression
matrix green; no color-only or isolated-control profile.

### R7.5 — product editor and authoring ergonomics

1. Keep Standard at the current 13 controls unless a new control passes every
   admission requirement and remains under the owner-controlled maximum of 15.
2. Keep Pro at seven capability IDs; expose 20-30 grouped editor fields as
   projections rather than inventing capability IDs for UI convenience.
3. Present Expert as a searchable domain/part browser with type, bounds,
   current value, default, scope, preview and invalid-value feedback; never as
   hundreds of sliders.
4. Make every editor field derive from canonical metadata: group, order, label,
   help, control kind, plan and preview fixture.
5. Preview at least desktop, narrow container and mobile; light/dark or mode
   previews follow the tenant's declared modes rather than an unrelated toggle.
6. Validate contrast/APCA, bounds, unsafe combinations, static/DB parity and
   exact restore before export.
7. Export and re-import the canonical bounded document without loss. Unknown,
   hostile, non-finite, excessive or disallowed values fail closed with one
   named error and do not partially apply.
8. Show impacted groups/families from the generated control-impact graph so an
   operator understands reach before publishing.

Exit: Standard remains small/high-leverage; Pro is product-comprehensible;
Expert is usable but bounded; every field has metadata, preview and causal
impact; round-trip and invalid-value drills pass.

### R7.6 — catalog breadth disposition

1. Compare local primitive capabilities with the external headless catalogs,
   including complex collections, focus/overlay systems, forms, pickers,
   navigation, drag/drop, virtualization and mobile interaction patterns.
2. Compare patterns, charts, structures and surfaces by product capability,
   not by a one-to-one external name search.
3. For a suspected gap, search canonical local exports, compatibility aliases,
   compounds and higher-layer compositions first.
4. Improve an existing family when the behavior belongs to its current
   contract.
5. Propose a new family only when there is a real reusable product capability,
   no canonical equivalent, a stable accessible anatomy, at least two plausible
   product consumers and a maintenance/testing owner.
6. Record dependency, license, bundle, SSR, browser, accessibility and
   migration consequences if an external headless implementation is proposed.
7. New-family proposals do not enter the 252 denominator or production source
   during R7; they receive a separate owner decision and work order.

Exit: every external benchmark capability has a disposition; zero duplicate
families; actionable follow-on proposals are bounded and separately owned.

## Parallel execution and machine budget

R7 optimizes wall-clock time without multiplying shared writers or heavy
processes.

- Opus MAIN owns the conflict graph, architecture, canon and integration.
- One Fable lane may advise read-only on architecture, behavioral parity and
  visual coherence.
- Up to two Sonnet lanes may perform disjoint family mappings, ledgers, exact
  wiring, i18n and structured evidence.
- Additional read-only scouts are permitted only when they do not duplicate
  repository discovery or compete for the same context and machine resources.
- Shared contracts, compiler, generated CSS, i18n merge, harness and canon have
  one writer at a time.
- There is at most one heavy build/test process, one server and one Chromium.
- Family lanes do not run builds or browsers. They return durable JSON receipts
  under the coordinator-owned temporary root and release ownership.
- MAIN works in long checkpoint-sized iterations and does not stop for
  reversible implementation choices already resolved by this contract.
- Codex performs compact telemetry checks and intervenes only at a checkpoint,
  verified stall or hard external blocker.

Throughput is measured in admitted family/part/property triples and closed
cohorts, never agent count, tokens written, files visited or screenshots taken.
