# Two-track operating protocol

The consumer contract ([`../index.md`](../index.md)) says WHAT an application
may import. This document says HOW the two tracks operate against it without
either one waiting on the other: how the design system releases, how an
application pins and upgrades, and how an application asks for a capability the
design system does not have yet.

It is the executable half of contract §7. Where §7 names the four decoupling
mechanisms, this document defines each one and names the check that enforces
it.

| Mechanism | Enforced by |
|---|---|
| A guaranteed-surface change carries a changeset | `packages/core/scripts/check/contract-changeset/index.mjs`, run by the `changeset` job of `.github/workflows/ci.yml` |
| An application pins an exact version | the application's own `package.json`, reviewed in its repository |
| One request path for a missing capability | the roadmap `new_work` rule (`roadmap/README.md`) |
| The contract diff is published | the "Contract diff" section of [`../../../../../roadmap/STATUS.md`](../../../../../roadmap/STATUS.md), generated by `pnpm roadmap:status` |

## 1. The two tracks

| Track | Repository | Owns | Never touches |
|---|---|---|---|
| DS | `ui-design-system` | the package behind the contract; publishes versioned releases | any application repository; the §2 signatures and the §3 schema of the contract |
| APP | `app-bithire` (the only APP track in flight, owner 2026-09-05) | its screens, against the contract; records its work in `app-bithire/roadmap/` | design-system internals; unsanctioned subpaths; tenant CSS |

Neither track blocks the other. The DS track lands waves behind the contract
and publishes; the APP track keeps building against the version it pinned and
upgrades when it chooses.

## 2. Release discipline

### 2.1 Every shipped change carries a changeset

A pull request that changes anything under `packages/core/` that ships must add
a changeset. Three path classes, three answers:

| Class | Paths | Requirement |
|---|---|---|
| signature | `packages/core/src/entrypoints/**`, `packages/core/contracts/package/entrypoints/**` | a changeset **and** a `contract-diff` block |
| contract | `packages/core/docs/consumer-contract/**` | a changeset |
| exempt | `packages/core/docs/**` outside the consumer contract | none — those documents are not in the package's `files` and never reach a pinned consumer |
| library | the rest of `packages/core/**` | a changeset |

A path class is not the whole answer, because an entrypoint is a barrel and the
declarations it publishes live where they are DEFINED. So the check also derives
the **signature surface** from the exported declarations themselves: it resolves
every published subpath of `exports` to the module that declares each name, and
compares that declaration's shape — its text with function bodies elided —
across the range.

| Also required | When |
|---|---|
| a `contract-diff` row naming the symbol | a published declaration is ADDED, REMOVED, or changes shape, wherever it is defined |
| the changeset bumps `@rottay/design-system` | always — a block inside a changeset that bumps another package travels with that package's release notes and reaches nobody pinned to this one |

When a name is declared more than once, the shape is every declaration that a
caller can see. A function's OVERLOAD signatures are its contract and its
implementation signature is not — TypeScript hides that one from every caller —
so changing an overload's return type is a contract event and widening the
implementation behind unchanged overloads is not.

The derivation fails closed. A published subpath whose source module cannot be
located, and a name inside one that the resolver cannot follow, are reported as
findings rather than skipped: the symbols behind an unresolvable input are
missing from both ends of the comparison, so every one of them would read as
unchanged and be asked for nothing.

An implementation change behind an unchanged signature owes nothing beyond its
changeset: rewriting a function body is not a contract event. Adding a field to
`MountTenantThemeOptions` is, even though that interface is declared several
directories away from `src/entrypoints/`. The range that changed 74
public-contract paths and was asked for nothing is the reason this paragraph
exists.

The check counts only the changesets the pull request ADDS. A changeset already
committed on the base branch — the retained 3.0 changeset of WO-RET-01 is one,
and stays one until it is published — describes its own release, not the range
that follows it. This is deliberate: the previous inline CI step asked whether
any changeset file existed at all, which the repository itself satisfied on
every branch, forever.

Run it before committing:

```bash
node packages/core/scripts/check/contract-changeset/index.mjs --base=main
```

### 2.2 The `contract-diff` block

A signature change states what moved, in the changeset, in a fenced block the
status tool reads:

````markdown
---
"@rottay/design-system": minor
---

Adds the retained artifact input to the mount facade.

```contract-diff
signature ./server#mountTenantTheme — accepts the retained `artifact` input
subpath ./commercial — removed; the root barrel is the public way
export .#DetailSurface — added
```
````

The grammar is closed and fail-closed: `<kind> <target> — <detail>`, one row per
line, `kind` one of `subpath`, `signature`, `export`, `target` a package subpath
(`<subpath>#<symbol>` for a signature or an export), separator an em dash. A row
that does not parse fails the check and fails `pnpm roadmap:status`; it is never
read as an absent declaration.

There is no second ledger. The changesets are the source; the check enforces
them; STATUS republishes them.

### 2.3 Semver, as this contract means it

| Bump | What it may do |
|---|---|
| patch | anything invisible to a consumer: internals, a document, a fix that changes no signature |
| minor | ADD to the guaranteed surface — a new subpath, a new export, a new optional input |
| major | REMOVE or narrow anything guaranteed. Only through the 3.0 changeset of WO-RET-01, and only with a codemod |

A removal without a codemod is not a major, it is an outage in another
repository. The APP track is entitled to a mechanical migration for everything
the contract guaranteed.

### 2.4 Retained inputs

An input of a §2 signature is RETAINED once it is published: a later work order
may reimplement everything behind it, but must keep accepting it.

The named instance is `MountTenantThemeOptions.artifact`, introduced by
WO-CON-02. WO-EMI-02 replaces the facade with the real mount and keeps
accepting the option: it verifies the supplied artifact's digest AND its bytes
against its own compile and refuses a mismatch by name. Two independent answers
to one question is what that verification is for.

The option may be retired only as a breaking change on this track — the 3.0
changeset of WO-RET-01, carrying its own codemod, announced through the contract
diff. Removing it behind an implementation swap would break every layout the
WO-CON-02 codemod migrated, which is the application-touching landing WO-CON-02
exists to prevent.

The same rule governs every future input of a §2 signature. "The implementation
no longer needs it" is not a reason to drop an input; it is a reason to verify
it.

## 3. Version pinning, for the APP track

1. **Pin the exact version.** `"@rottay/design-system": "2.19.36"` — no caret, no
   tilde, no range. A range makes an install date part of the build, and a build
   that changes without a commit cannot be bisected.
2. **No `workspace:*` and no local link in a production build.** They resolve to
   whatever is on that machine, which is the opposite of a pin. A local link is
   for reproducing a design-system bug from the application, in a branch that
   never merges.
3. **Upgrade on the application's own schedule.** Nothing in the design-system
   roadmap requires an application to upgrade on a date. The contract diff tells
   the APP track when an upgrade is worth its time.
4. **One version per application.** Two pins in one repository means two
   contracts, and the lint rule can only enforce one.

## 4. The upgrade checklist

When the APP track decides to move its pin:

1. Read the contract diff in `roadmap/STATUS.md` for every version between the
   current pin and the target. `subpath` and `export` rows tell you what to
   import; `signature` rows tell you what to re-read.
2. Read the changelog entry of every major in the interval and run the codemod
   it names, in the order the release notes give.
3. Move the pin to the exact target version and install.
4. Run the application's typecheck. A guaranteed signature that changed shape
   without a major is a design-system defect — report it as one; do not adapt
   the application around it.
5. Run `@rottay/no-unsanctioned-ds-subpath`. A new red here means the upgrade
   retired a subpath the application still imports; the codemod of step 2 should
   have moved it.
6. Run the application's own suites and its visual evidence.
7. Record the upgrade in `app-bithire/roadmap/`, naming the version and the
   codemods run.

If step 4 or 5 fails on something the contract guaranteed, stop and file the
capability request of §5 instead of working around it locally. A local
workaround is how a second design system starts.

## 5. Asking the design system for a capability

### 5.1 The promote-to-DS test

> Could another application use this without knowing what a tenant, candidate,
> role, company, interview or event IS?

- **Yes** — it belongs in the design system. File the request below.
- **No** — it belongs in the application. Build it there, in its own feature
  folder.

The test is about the CAPABILITY, not the appearance. Shared capability does
not mean the products look alike: layout, rhythm, narrative and copy stay with
the application.

### 5.2 What is never the answer

- A `_shared/` bridge in the application that re-implements a design-system
  tier. `_shared/` is app-internal grouping, not a second design system; a
  capability that passes the promote-to-DS test must not land there.
- An inline restyle of a design-system component — `style={{}}`, a wrapper class
  that overrides a skin, a copy of an engine file. A component's appearance is
  moved by the tenant theme and by the props the component publishes, never by
  a consumer reaching into it.
- A local fork of the package, a patched `node_modules`, or a vendored copy.
- Importing a subpath the contract does not list as `guaranteed`. The lint rule
  refuses it, and the refusal is the correct answer.

### 5.3 The request

One path, and it is the roadmap's `new_work` rule (`roadmap/README.md`): a new
`### WO-` block in the lane file the capability belongs to, plus its registry
entry. `pnpm roadmap:check` enforces the pairing. There is no other channel —
no issue, no document, no message that becomes work.

The block states:

```markdown
### WO-XXX-nn <title>
- **Outcome** — what an application can do afterwards that it cannot do today,
  in the application's own terms.
- **Why** — the concrete screen or flow that needs it, and what the APP track
  is doing meanwhile.
- **Promote-to-DS** — the answer to §5.1, argued: the capability stated without
  a single domain noun, plus the second consumer that would use it.
- **Tier** — primitive, pattern, structure or surface, and why that tier
  (`CLAUDE.md`, the four-tier taxonomy).
- **Depends on** — the work orders that must land first.
- **Acceptance gate** — the mechanical check that closes it.
- **Size** — S / M / L.
```

### 5.4 Acceptance of a capability request

A request is accepted when all four hold. Any one of them failing sends the
work back to the application:

1. It passes the promote-to-DS test with a domain-free statement.
2. It names a real consumer, and a plausible second one. "Used twice" is not by
   itself a reason to promote.
3. It maps to exactly one tier and one family, with one owner. A capability that
   needs two owners is two requests.
4. It carries no product semantics: no tenant, candidate, role, company,
   interview or event, in the name, the props or the copy.

While the request is open the APP track is not blocked: it builds the screen in
its own repository with its own component, and replaces it with the
design-system capability when that lands. What it must not do is generalise the
local component into a parallel design system while waiting.

## 6. The contract diff

`pnpm roadmap:status` publishes a "Contract diff since `<version>`" section in
`roadmap/STATUS.md`. The reference is the version in
`packages/core/package.json` — the last one an application can pin — and the
rows are the `contract-diff` declarations of every changeset pending since it.

The section is empty when no pending changeset declares a public signature or
subpath change, and it says so. An empty diff is a real answer: the design
system moved and nothing an application imports did.
