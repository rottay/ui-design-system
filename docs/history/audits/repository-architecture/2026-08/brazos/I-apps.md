## Hallazgos (ordenados por severidad)

### H-I-1 · BLOQUEANTE · El próximo repin del DS rompe la hoja de estilos completa de app-platform
- Qué: `app-platform/src/app/globals.css:14` hace `@import '@rottay/design-system/dist/platform.css';` y otros 3 sitios (`src/app/docs/layout.tsx:12`, `src/app/(landing)/layout.tsx:1`, `src/app/(auth)/login/page.tsx:16`) hacen `import '@rottay/design-system/commercial.css'`. Ninguno de los dos artefactos existe hoy en el DS fuente (`ui-design-system/packages/core`, versión local 2.19.36).
- Evidencia:
  - `ls ui-design-system/packages/core/dist/*.css` → sólo `bithire.css, evnto.css, modern-engine.css, rottay.css, styles.css`. Sin `platform.css` ni `commercial.css`.
  - `packages/core/package.json` `exports` no declara `./commercial.css` ni `./dist/platform.css` como entrypoints nombrados (sólo el glob catch-all `"./dist/*.css": "./dist/*.css"`, que resuelve al archivo físico — y el archivo no existe).
  - `node -e "require('./dist/foundation/tokens/ts/presentation/brand-themes/index.js').FIRST_PARTY_VERTICAL_ROSTER"` → `["Rottay","BitHire","Evnto"]`. "Platform" no es ni fue nunca un vertical DS de primera clase.
  - `packages/core/scripts/verticals/platform-identity-zero-gate/index.mjs` (gate dedicado, existe HOY, corre en `pnpm lint`): declara `RETIRED = 'plat'+'form'` (ofuscado a propósito para no auto-matchear) y una `CONTENT_RULES.bundle-path` que prohíbe explícitamente `dist/platform.css` o `platform.css` en cualquier archivo del repo DS. Es decir: el DS activamente **certifica que `platform` como bundle está retirado**.
  - `commercial.css` no tiene build target en `packages/core/package.json` (0 menciones de `"commercial"`); el único `commercial.css` que existe en el repo DS está en `test-artifacts/release/2.19.29/unpacked/package/dist/commercial.css` — un artefacto de release histórico, no algo que el código fuente actual produzca.
  - Hoy `app-platform/node_modules/@rottay/design-system/dist/` (paquete INSTALADO, pin 2.19.35) SÍ tiene `platform.css` y `commercial.css` — por eso platform compila hoy. Es deuda dormida, no un error visible.
- Impacto en el objetivo del owner: en el próximo `pnpm up @rottay/design-system` o repin (rutina en este monorepo — ver memoria "repin-cascade-method"), `next build` de app-platform falla al resolver 2 imports CSS inexistentes, o peor, el build pasa silenciosamente sin esas hojas de estilo y toda la superficie que dependía de `platform.css`/`commercial.css` pierde su CSS base (violación directa de "premium, sin espacios en blanco" — se rompe TODA la app, no una primitiva puntual).
- Optimización concreta: (a) migrar `globals.css` a `@import '@rottay/design-system/styles/rottay';` (o el nombre de vertical real que platform usa, dado que no es un vertical de primera clase — necesita decisión de producto: platform ¿es "rottay" tenant o necesita su propio bundle vertical?); (b) para `commercial.css`, decidir si el `roadmap-commercial` program (mencionado en CLAUDE.md raíz) va a reintroducir un `commercial.css` con nombre estable, y si no, eliminar los 3 imports muertos; (c) agregar un gate en app-platform que falle si el import CSS de `@rottay/design-system` no resuelve contra los `exports` declarados del paquete instalado (detectaría esto antes del próximo repin en vez de después).

### H-I-2 · ALTO · evnto impersona su propia identidad ante un fallo de resolución de tenant DB
- Qué: `app-evnto/src/core/lib/tenancy/get-tenant-branding.ts` envuelve la consulta DB en un `try { ... } catch { return null; }` con el comentario explícito `// A database outage falls back to the static same-slug Evnto baseline.` (línea previa al `catch`). `app-evnto/src/app/layout.tsx` nunca llama `notFound()`: con `branding === null` renderiza igual, con `data-vertical="evnto"` y sin artefacto (`rootThemeAttributes` cae al branch estático de `resolveEvntoRuntimeThemeSsrState`).
- Evidencia: `app-evnto/src/core/lib/tenancy/get-tenant-branding.ts` (bloque try/catch antes del `return selected ? buildBrandingResponse(...) : null`); `grep -rn "notFound" app-evnto/src/app/layout.tsx app-evnto/src/core/lib/tenancy/` → 0 resultados.
- Contraste directo: `app-bithire/src/core/lib/tenancy/get-tenant-branding/index.ts` documenta lo opuesto como ley: `"Infrastructure errors intentionally propagate: a custom tenant must fail closed instead of rendering the BitHire identity."` y `app-bithire/src/app/layout.tsx` llama `notFound()` cuando `branding` es `null` para un tenant no-bundled.
- Impacto en el objetivo del owner: un tenant custom de Evnto (dominio propio, DB whitelabel activo) que sufre una consulta DB fallida (timeout, réplica caída, fila borrada) no ve un error — ve el shell genérico de Evnto bajo SU PROPIO dominio, sin ninguna marca de que algo falló. Esto es exactamente lo que el propio código de bithire fue escrito para evitar ("must never render BitHire by accident").
- Optimización concreta: alinear evnto con el patrón de bithire — separar "tenant no existe / slug inválido" (→ `null` legítimo, cae a evnto por diseño de producto si así se decide) de "la consulta DB falló" (→ debe propagar y fallar cerrado, o al menos usar el mismo patrón de recuperación acotada `last-known-valid` que bithire ya implementa en `runtime-tenant-theme/artifact-resolution`). El pipeline de compilación de evnto (`artifact-resolution/index.ts`) YA tiene cache/LKV — el defecto está sólo en el nivel de arriba (`get-tenant-branding.ts`), lo cual hace el fix acotado.

### H-I-3 · ALTO · app-platform: el shell vivo no prueba pintar un tenant DB, y no lo hace por SSR
- Qué: dos problemas relacionados. (1) `app-platform/src/app/(dashboard)/layout.tsx` y `src/core/providers/dashboard-providers/index.tsx` (`'use client'`) pasan `tenantConfig`/`runtimeAppearance` a `<DesignSystemProvider>` sin que ningún layout de la app inyecte un `<style dangerouslySetInnerHTML>` server-side (verificado: 0 ocurrencias de `<style`/`dangerouslySetInnerHTML` en los 4 `layout.tsx` que llaman `getTenantBranding`). bithire y evnto SIEMPRE inyectan el artefacto compilado inline en `<head>` antes del primer paint. (2) `app-platform/tests/e2e/` tiene 5 specs planos (`navigation, visual-regression, users, a11y, auth`) y CERO referencias a `tenant`, `whitelabel`, `TenantThemeDocument` o a un segundo tenant — pese a ser la única de las 3 apps con un editor completo de temas.
- Evidencia: `grep -rn "<style\|dangerouslySetInnerHTML" app-platform/src/app/layout.tsx app-platform/src/app/docs/layout.tsx "app-platform/src/app/(auth)/layout.tsx" "app-platform/src/app/(dashboard)/layout.tsx"` → 0; `app-platform/src/core/providers/dashboard-providers/index.tsx:41` `'use client';`; `find app-platform/tests/e2e -maxdepth 1 -type f` → 5 archivos, ninguno con "tenant"/"whitelabel" en el nombre ni el contenido (`grep -rlE "tenant-canary|themanagement|TenantThemeDocument|toHaveScreenshot" app-platform/tests/e2e` → vacío).
- Impacto en el objetivo del owner: platform ES la app que administra tenants — es donde el owner (o un operador) más necesita ver el resultado real de una customización. Sin inyección SSR hay riesgo de FOUC/flash del tenant equivocado en la app real (no confirmado si `DesignSystemProvider` lo mitiga internamente — señal para cruzar con el cluster de theme-model); sin e2e no hay prueba reproducible de que "parecer un producto distinto" ocurra fuera de la vista previa aislada del editor (`previewSrcDoc`, un iframe con srcdoc, ver H-I-3b abajo).
- Optimización concreta: (a) confirmar con el cluster A/F si `DesignSystemProvider` evita FOUC internamente pese al boundary `'use client'`; si no, mover la inyección de `runtimeAppearance` compilado a un `<style>` SSR en `(dashboard)/layout.tsx`, igual que bithire/evnto; (b) portar (o generalizar) `two-systems/divergence.spec.ts` de bithire a platform, apuntando el editor real de `tenant-theme-console` contra dos tenants seedeados.

### H-I-4 · MEDIO · evnto declara 2.19.29, ejecuta 2.19.36 vía symlink manual sin registrar la deriva
- Qué: `app-evnto/package.json:72` fija `"@rottay/design-system": "2.19.29"`, pero `node_modules/@rottay/design-system` es un symlink manual a `ui-design-system/packages/core` (versión local actual: 2.19.36, confirmada en `package.json` y `dist/build-stamp.json`).
- Evidencia: `readlink app-evnto/node_modules/@rottay/design-system` → `/Users/daniel/Developer/Rottay/ui-design-system/packages/core`; `grep '"version"' ui-design-system/packages/core/package.json` → `2.19.36`.
- Impacto en el objetivo del owner: todo lo que se prueba en desarrollo de evnto corre contra 2.19.36 (7 versiones patch adelante de lo declarado); un `pnpm install` limpio sin el symlink manual instalaría 2.19.29 desde el registro — una superficie completamente distinta (7 versiones de diferencia en un programa que está reescribiendo activamente el compilador de temas). El comportamiento "probado" en dev nunca es el que un CI/build limpio ejecutaría.
- Optimización concreta: repin `app-evnto/package.json` a 2.19.36 (o a la versión que realmente se quiere congelar) y documentar en `app-evnto/CLAUDE.md` el mismo patrón `USE_LOCAL_DS` que usa app-platform (symlink explícito y auditable vía script, no manual y silencioso).

### H-I-5 · MEDIO · app-platform: 8792 `style={{` y 229 `<div>` crudos fuera de la excepción marketing
- Qué: conteo re-verificado (ver metodología arriba). app-platform tiene 326 archivos `.tsx` (fuera de `landing/marketing/showroom`) con `style={{`, sumando 8792 ocurrencias; evnto 234 archivos / 5939 ocurrencias; bithire 53 archivos / 91 ocurrencias. Los `<div>` crudos: platform 229 ocurrencias en 37 archivos (excluyendo el falso positivo legítimo `src/app/docs/opengraph-image.tsx`, que usa la API `next/og` `ImageResponse` — Satori no interpreta JSX real, exención documentada in situ); evnto y bithire ~6-7 ocurrencias totales, casi todas en una página de callback de auth pre-provider o en tests.
- Evidencia: comandos en la sección de metodología arriba; top ofensores platform: `identity/users/screens/overview/index.tsx` (32 `<div>`), `(auth)/login/narrative-panel/witness-strip/index.tsx` (30), `tenant-theme-console/index.tsx` (16, dentro del iframe srcdoc — exención razonable), familia `compliance/docs/components/docs-atlas/*` (48 combinadas entre 7 archivos).
- Impacto en el objetivo del owner: la mayoría de los `style={{` inspeccionados SÍ encadenan `var(--ds-*)` (no son colores hardcodeados), pero es una cantidad masiva de estilo inline en vez de composición vía primitivas DS (`Box`/`Flex`/`Stack`), lo cual es exactamente lo que CLAUDE.md prohíbe ("NEVER use raw HTML elements", "Do not hardcode... use DS tokens" se cumple parcialmente vía `var()`, pero el patrón arquitectónico se viola sistemáticamente). `identity/users/screens/overview/index.tsx` es una pantalla de producto central, no un caso de borde.
- Optimización concreta: priorizar el drenaje por el archivo/feature de mayor concentración (`identity/users/screens/overview`, la familia `docs-atlas`, `compliance/*`), migrando a `Box`/`Flex`/`Grid` con props de tema en vez de `style={{ ...var(...) }}` inline — mismo patrón que bithire ya demuestra funcionar a esta escala (53 archivos vs 326).

### H-I-6 · MEDIO · Hex "pelado" (sin fallback `var()`) sólo en app-platform
- Qué: 6 archivos de app-platform declaran color hex directo sin encadenar a un token DS: `organization/settings/screens/overview.tsx` (`border: '1px solid #d9d9d9'`), `organization/admin/screens/sessions/overview.tsx` (`color: '#fff'` × 5). El resto de los hits hex en tsx (`device-policy.tsx`, `security-sessions.tsx`, `security-devices.tsx`) usan el patrón defendible `var(--ds-color-x, #hex)` (fallback, no autoridad). bithire y evnto: 0 hex pelados en tsx.
- Evidencia: `find app-platform/src -name "*.tsx" -print0 | xargs -0 grep -noE "style=\{\{[^}]*#[0-9a-fA-F]{3,8}[^}]*\}\}"` → 19 líneas en 5 archivos + 1 más aislado.
- Impacto: violación literal y puntual de "NEVER use hardcoded colors" (CLAUDE.md raíz), acotada — no afecta el skin global, sólo esas 6 pantallas.
- Optimización concreta: reemplazar `#d9d9d9`→`var(--ds-color-border)`, `#fff`→`var(--ds-color-text-inverse)` o el token equivalente; 6 ediciones puntuales, sin riesgo arquitectónico.

### H-I-7 · BAJO · `color-mix()` con peso hardcodeado alto diluye la fidelidad del tenant en bithire
- Qué: `app-bithire/src/styles/detail-editor-chrome.css` mezcla `var(--ds-color-primary)` con un literal hex a pesos de 28-56% para el literal (`color-mix(in srgb, var(--ds-color-primary) 44%, #4a9fc1)`, `... 38%, #4a9fc1`, `... 72%, #438eaa`, `... 48%, #438eaa`).
- Evidencia: `app-bithire/src/styles/detail-editor-chrome.css:193,203,1274,1586`.
- Impacto: en las líneas con peso ≤48% para el token DS, el literal domina el resultado — dos tenants con `--ds-color-primary` opuestos convergerían a un tono azul similar en ese detalle, contradiciendo la ley F4A ("un leaf que re-expresa el color debe derivar", no diluir).
- Optimización concreta: revisar si esos 4 sitios pueden subir el peso del token DS (≥70%) o usar directamente un token de tinte ya calibrado (`--ds-color-primary-tint-*`) en vez de un literal ad hoc.

## Lo que está bien (con evidencia)

- **bithire, pipeline de theme→DOM (óptica 79)**: arquitectura ejemplar. Compila en request-time (no lee un artefacto publicado), cachea acotado (`MAX_CACHE_ENTRIES = 128`, `setBounded`), tiene 3 niveles de recuperación (`fresh` → `last-known-valid` en memoria → `last-known-valid` desde historial publicado del MISMO tenant) y nunca sustituye la identidad BitHire para un tenant custom (`RuntimeTenantThemeUnavailableError` cruza la frontera del server y hace fallar la request). `contracts/index.ts::isRuntimeTenantThemeResolution` re-valida en el cliente TODO el envelope (digest, selector, coverage, scopes) antes de aceptar una respuesta del endpoint de refresh — defensa en profundidad real, no cosmética.
- **hooks-manifest.json como frontera viva (óptica 85)**: de 165 asignaciones de `--ds-*` en el CSS propio de bithire (91 nombres distintos), el 100% está declarado en `publicHooks` (91/91) y todas las asignaciones muestreadas viven en selectores con scope (`[data-anatomy-*] .rt-app-shell`, nunca `:root`) encadenando `var(--ds-*)` en el valor. La ley del namespace (`app-platform/CLAUDE.md` "CSS Custom-Property Namespace Law") se cumple en la práctica, no sólo en el papel.
- **branding-bounds de platform (óptica 82)**: `boundedVisualString`/`boundedAssetUrl` bloquean control chars, `javascript:`, `@import`, `url()`, protocolo no-http(s), backslash en rutas — es un allowlist real con `reportDrop` auditable, no un passthrough con nombre de allowlist.
- **`two-systems/divergence.spec.ts` de bithire (óptica 88)**: única prueba de las 3 apps que demuestra el objetivo central del owner ("dos tenants deben parecer productos distintos") de punta a punta en la app real — captura screenshot + diff de píxeles con piso por ruta, evidencia de anatomía en polos opuestos, y falla explícitamente si el runtime theme style tag no aparece para el tenant DB o SÍ aparece para el bundled.
- **Consumo de imports JS del DS (óptica 84)**: las 3 apps import exclusivamente por subpaths declarados (`/icons`, `/server`, `/motion`, `/charts/*`, `/commercial` [platform], `/marks`) — cero `from "@rottay/design-system/dist/..."` o `/src/...` en código JS/TS. El único subpath profundo roto es el `@import` CSS de platform (H-I-1).

## Preguntas que no pude cerrar (y qué haría falta)

- **¿`DesignSystemProvider` evita FOUC pese al boundary `'use client'` en platform?** Necesita leer la implementación del provider en `ui-design-system/packages/core/src` (fuera del alcance de "apps"); relevante para cerrar H-I-3. Sugiero cruzar con el brazo de theme-model (A/F).
- **¿Qué pasa realmente en producción cuando `dist/platform.css` falta?** No pude ejecutar `pnpm build` (regla read-only). El razonamiento de H-I-1 es por inspección de `exports`/`dist`/gate, no por una build real fallida — alta confianza pero no observada en vivo.
- **¿El `catch { return null }` de evnto (H-I-2) es intencional de producto o deuda?** El comentario en el código lo presenta como diseño deliberado ("falls back to... baseline"), no como bug — vale la pena una confirmación de producto antes de tratarlo como defecto puro, aunque contradice directamente la ley que bithire documenta para el mismo problema.
- **Duplicación real de componentes (óptica 86)**: sólo pude muestrear 2 de ~50 carpetas candidatas en bithire por límite de tiempo. El patrón sancionado (`detail/form/table/card`) explica la mayoría, pero no descarto 1-2 reimplementaciones genuinas sin verificar.
