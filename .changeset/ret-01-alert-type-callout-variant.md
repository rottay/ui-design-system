WO-RET-01 (RET-01-ALERT-CALLOUT). Three deprecated names retire from the public contract: the `type` prop of `Alert` (declared on `AlertSharedProps`, published as `AlertProps.type`), the `variant` prop of `Callout` (`CalloutProps.variant`) and the type `CalloutVariant`. `tone` is the only semantic colour prop of both components, and the value `error` is spelled `danger`. `Callout` itself is NOT retired: it stays published and deprecated until 4.0, because on the Classic and Rustic engines it is the only implementer of the action tray, the callout tint set and the title-above-body layout. The census covers `packages/core/src`, `packages/showroom/src` and the `src` roots of app-bithire, app-evnto and app-platform (2026-10-03, the codemod kit in dry-run with the entries of this lot).

`AlertProps.type` -- removed; `tone` is the semantic colour. The four values map one to one: `info` -> `info`, `success` -> `success`, `warning` -> `warning`, `error` -> `danger`. Every engine resolved `tone ? TONE_TO_ALERT_TYPE[tone] : type` and read `type` nowhere else, so the mapped `tone` renders the same markup as `type` did. Measured by rendering the old prop at the previous commit and the mapped tone after this lot, per engine: the four values in three shapes (message only; message, description, icon and dismiss; body-only compact) plus the default, 13 of 13 identical on Modern, on Classic and on Rustic. An `Alert` that states neither renders the `info` surface, before and after.

`CalloutProps.variant` -- removed; `tone` is the semantic colour, with the same four-value map. The three Callout renderers (Classic, Rustic and the Modern presentation owned by Alert) resolved `tone ? TONE_TO_VARIANT[tone] : variant` and read `variant` nowhere else. Measured the same way: four values in three shapes (titled; title, icon, action and dismiss; body only) plus the default, 13 of 13 identical on each of the three engines.

`CalloutVariant` -- the type is no longer exported. It was reached only through `CalloutProps.variant`; no file of the showroom or of the three apps imports the name. `CalloutTone` types the `tone` prop. It is not a drop-in rename: `CalloutTone` spells `danger` where `CalloutVariant` spelled `error`, so a value typed by the old name is rewritten with its type.

`Callout` -- kept. Its `@deprecated` marker stays and its ledger row moves to WO-RET-06 with release line 4.0. On the Modern engine `<Alert tone message description action emphasis="subtle" announce="tone" />` renders the markup of `<Callout tone title action>{body}</Callout>`, with one difference in dismissal: a title change re-opens a dismissed Alert where the Callout stayed shut. On Classic and Rustic `Alert` drops `action` and paints a different tint set, so no application is asked to leave `Callout` in 3.0.

The Classic and Rustic engines are frozen and still read `type` (Alert) and `variant` (Callout) from the props they receive. Each member stays on a family-internal engine props type that is not published; the family entries publish the narrowed contracts as `AlertProps` and `CalloutProps`. Typed callers cannot state either member. A caller that passes one untyped (a spread, a cast) is still honoured by Classic and Rustic and is no longer read by Modern, where the Alert or the Callout then renders the `info` surface. On Modern the announcement follows the same key wherever it follows the tone: a `Callout`, or an `Alert` with `announce="tone"`, that carried an untyped `warning` or `error` goes from `role="alert"` to `role="status"`; an `Alert` on the default `announce` keeps `role="alert"`. `ALERT_DEFAULTS.type` and `CALLOUT_DEFAULTS.variant` keep their keys (the defaults those two engines read), and `CALLOUT_COLORS` keeps its four keys and values. `AlertType` stays exported in this lot, with no published member left that uses it (`ALERT_DEFAULTS` is family-internal and not published by the package root); retiring that export is owed inside WO-RET-01 with its own changeset row.

What an application must change. All of it fails at compile time on upgrade, except a spread:

- Run `pnpm -C packages/core codemods --write <app>/src`. It renames `type` to `tone` on every element it resolves to the design-system `Alert`, renames `variant` to `tone` on every design-system `Callout`, and maps the string literal (`error` becomes `danger`). Measured: app-bithire 1 `Alert` site (`src/core/auth/components/session-security/impersonation-banner/index.tsx`); app-evnto 69 `Alert` sites in 30 files and 7 `Callout` sites in `src/features/identity/profile/surface/screens/account/index.tsx`; app-platform 127 `Alert` sites in 56 files.
- Read the reported sites; the codemod does not edit them. Every one is a value that is not a string literal (a ternary or an identifier). Rename the attribute to `tone` and change each `'error'` the expression can yield to `'danger'`. app-evnto, `Alert` (5): `src/features/events/surface/screens/finance/index.tsx`, `src/features/payroll/surface/screens/record/periods/listing/index.tsx`, `src/features/payroll/surface/screens/workflows/settlement-processing/index.tsx`, `src/features/scheduling/surface/screens/record/listing/index.tsx`, `src/features/scheduling/surface/screens/workflows/calendar/index.tsx`. app-evnto, `Callout` (1): `src/features/identity/profile/surface/screens/account/index.tsx`. app-platform, `Alert` (9): `src/features/identity/profile/surface/screens/security/overview/index.tsx`, `src/features/organization/settings/surface/screens/billing/index.tsx`, `src/features/organization/settings/surface/screens/mfa/index.tsx`, `src/features/organization/tenants/surface/screens/record/detail/view/tabs/plan-and-limits/index.tsx`, `src/features/security/authentication/surface/screens/jwt/index.tsx`, `src/features/security/authentication/surface/screens/mfa/index.tsx`, `src/features/services/navigation/surface/screens/publishing/review/index.tsx`, `src/features/services/navigation/surface/screens/versions/history/index.tsx`, `src/features/services/notifications/surface/screens/providers/console/index.tsx`.
- An element that already states `tone` next to `type` or `variant` is reported: keep `tone` and delete the other. The census found none.
- A spread onto `Alert` or `Callout` compiles either way, so it is the one case the compiler does not catch: if the spread object carries `type` or `variant`, rename the key to `tone` and map `error` to `danger`. The codemod reports a spread it can see; the census found none on either component in the showroom or the three apps.
- The codemod also reports each file that imports `Callout` (app-evnto: one file, 8 elements). Nothing has to change there in 3.0 beyond `variant`; the report states what 4.0 will ask.

Inside the design system no productive site stated either prop when this lot began. The showroom moves 12 `Alert` sites to `tone` in this lot (`app/probe/ds-reference/sections/feedback` 7, `components/torture-sections/status-feedback` 5); its other four `Alert` sites and its one `Callout variant` site had moved before it. The showroom still renders `Callout` at 13 sites in four probe and torture files, all on `tone`; they exercise the component itself and stay.

No minor was published between the deprecations and 3.0.
