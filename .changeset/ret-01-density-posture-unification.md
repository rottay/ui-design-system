WO-RET-01 (F-84, density-posture unification). The package published two names for one axis: `DensityKey` (declared as the literal union `'compact' | 'comfortable' | 'spacious'` in the pattern data contracts) and `DensityPosture` (declared as `(typeof DENSITY_POSTURES)[number]` over the same three literals by the density runtime). They were value-identical and mutually assignable, so nothing distinguished them except the spelling. `DensityPosture` is the surviving name and the single public declaration; `DensityKey` leaves the package root. `ListToolbarProps.density`, `ListToolbarProps.onDensityChange`, `ListSurfaceToolbarConfig.density` and `ListSurfaceToolbarConfig.onDensityChange` are now spelled with `DensityPosture`; they accept and emit exactly the values they did before, so no call site that passes a literal or a `DensityPosture` value changes, and nothing renders differently. The Modern list-toolbar engine, the collection workspace and its render dispatch, and the two showroom probes that imported the retired name were migrated to `DensityPosture`.

The name is gone from the package and the showroom: no source file under `packages/core/src` or `packages/showroom/src` names `DensityKey`, and a test walks both trees to keep it so. The frozen Classic list-toolbar engine named the retired identifier at six type positions (its import specifier and five annotations); those six identifiers were substituted by `DensityPosture` under a written freeze exception recorded by the coordinator ("minimal shared-contract compile fix: type identifier DensityKey -> DensityPosture, no emitted change"). Nothing else in that file moved, and its transpiled JavaScript is byte-identical before and after. The list-toolbar contracts module re-exports the `DensityPosture` type from its owner so the frozen file keeps its single contracts import.

Not part of this change: the other density types stay as they are because they are different axes or component-local vocabularies (`Density`, `DensityProfile`, the two `DensityMode` declarations, `DensityPreference`, and the component-scoped `ActionDockDensity`, `SurfaceDensity`, `TooltipDensity`, `PopoverDensity`, `MarkdownDensity`, `DocumentDensityPosture`). F-84's criterion of a single `Density*` type is not met by this change and is not claimed.

Downstream apps: an import or re-export of `DensityKey` from `@rottay/design-system` fails at compile time on upgrade. Census by word search and by a read-only dry-run of the codemod kit over the three apps: one site per app and no other reader. `app-bithire/src/ui/tables/listing/toolbar/index.tsx` imports the name and exports it locally; `app-evnto/src/ui/tables/list-toolbar/index.tsx` and `app-platform/src/ui/tables/entity-table-workspace/types.ts` re-export it from the package. The codemod entry `symbol-removed/.#DensityKey` rewrites all three: an import moves to `DensityPosture` and its references follow, and an export specifier becomes `DensityPosture as DensityKey`, so each app module keeps exporting its own name and the app's own importers are untouched. The apps were not edited and no automatic upgrade is claimed; the rewrite runs when an app adopts 3.0.

```contract-diff
export .#DensityKey — removed; value-identical duplicate of `DensityPosture` (`compact | comfortable | spacious`); migrate to `DensityPosture` from the package root; codemod `symbol-removed/.#DensityKey` rewrites imports and turns re-exports into `DensityPosture as DensityKey`; census: showroom 2 files migrated, one site in each of the three apps
signature .#ListToolbarProps — `density` and `onDensityChange` are typed by `DensityPosture` instead of `DensityKey`; same three literals, no accepted or emitted value changes
signature .#ListSurfaceToolbarConfig — `density` and `onDensityChange` are typed by `DensityPosture` instead of `DensityKey`; same three literals, no accepted or emitted value changes
```
