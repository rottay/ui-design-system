WO-RET-01 (RET-01-MISC-PROPS). Three deprecated members retire from the public contract: `DataTablePatternProps.mobileBreakpoint`, `BadgeProps.overflowCount` (declared on `BadgeBaseProps`) and `SurfaceTabbedView.permissionId`. Each has a canonical replacement that renders or resolves the same for every measured consumer. The census covers `packages/core/src`, `packages/showroom/src` and the `src` roots of app-bithire, app-evnto and app-platform (2026-10-03); the showroom states none of the three.

`DataTablePatternProps.mobileBreakpoint` -- the pixel threshold below which `PatternDataTable` presented cards is removed with the measurement it owned (its own `ResizeObserver` and the viewport fallback). The table adapts on the shared postures only: with `autoMobileCards` (default `true`) the posture defaults present cards on a phone request or a compact box, and `adapt={{ compact: { presentation: "cards" } }}` declares it explicitly. A stated number has no numeric equivalent: the threshold now follows the shared container ladder. What an app must change: app-bithire forwards its table wrapper's own optional `mobileBreakpoint` to `PatternDataTable` at one site (`src/ui/tables/data-table/index.tsx`); no caller of that wrapper sets it, so the forwarded value is always `undefined`, the retired branch was never entered and the posture defaults already apply. Delete the attribute (and the wrapper's unused prop); the table renders the same. The attribute fails at compile time on upgrade until it is deleted. The codemod reports the site and does not edit it, because it cannot tell an always-undefined identifier from a stated number. `WorkspaceResponsiveConfig.mobileBreakpoint` is a different member (a ladder step on the collection workspace) and is unchanged.

`BadgeProps.overflowCount` -- the prop is removed; `max` is the cap. No engine honoured `overflowCount`: Modern defaulted `max` to 99 at destructuring, so `max ?? overflowCount` always yielded `max`, and Classic and Rustic never read it. `<Badge count={n} overflowCount={10} />` rendered the 99 cap on the three engines. What an app must change: app-platform passes `overflowCount={99}` to `Badge` at one site (`src/features/organization/admin/surface/screens/sessions/overview/index.tsx`); the value equals the default, so renaming it to `max` (or deleting it) renders the same. The codemod renames the attribute. A caller that stated any other number sees that number start to apply once renamed, which is what the prop documented. `BADGE_DEFAULTS.overflowCount` keeps its key (the default the three engines read for `max`), and antd's own `overflowCount`, which the Classic engine passes to the antd badge, is not this prop. `BadgeProps.variant` and `BadgeVariant` are out of this lot and unchanged.

`SurfaceTabbedView.permissionId` -- the member is removed; the access id of a tabbed view is `capabilityId ?? key`. The marker called it a type-only migration alias. That was wrong: `filterSurfaceTabbedViews` read it after `capabilityId` in two places (visibility and the disabled projection). Both now read `capabilityId ?? key`. The same string under `capabilityId` yields the same access decision. What an app must change: app-evnto authors `permissionId` on two settings tabs (`src/features/admin/settings/surface/screens/general/index.tsx`, `payments` -> `billing` and `security` -> `security`), reads `tab.permissionId` in that screen's controller, and states it on two rows of the controller test. All of them fail at compile time on upgrade; rename the member to `capabilityId` and drop the controller's `?? tab.permissionId` read. The `payments` tab matters: its key differs from its access id, so a value left under `permissionId` through an untyped path would be looked up under `payments` and, under resolved access, fail closed. The codemod reports each import of `SurfaceTabbedView`; an object member is not an attribute list, so nothing is rewritten.

No minor was published between the deprecations and 3.0.
