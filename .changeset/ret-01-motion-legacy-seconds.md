WO-RET-01 (RET-01-MOTION-LEGACY-SECONDS). The eight deprecated un-suffixed timing props of the motion primitives retire: `duration` and `delay` on `BaseMotionProps` (and so on `FadeInProps`, `SlideInProps`, `ScaleInProps`, `StaggerChildrenProps` and `ScrollRevealProps`, which extend it), `staggerDelay` and `delayChildren` on `StaggerChildrenProps`, `delay` and `duration` on `TextRevealProps`, and `duration` and `delay` on `CountUpProps`. The replacements are the millisecond props that already existed beside them: `durationMs`, `delayMs`, `staggerDelayMs` and `delayChildrenMs`.

This removes a live runtime branch, not only types. Until now a value passed through an un-suffixed prop was read as seconds when it was positive and at most 10 (`0.32` became 320 ms) and as milliseconds otherwise (`320` stayed 320 ms); the `*Ms` prop won when both were stated. That interpretation is gone from the timing resolver and from `FadeIn`, `SlideIn`, `ScaleIn`, `StaggerChildren`, `TextReveal` and `CountUp`; no shim remains. The `*Ms` props behave exactly as before: milliseconds, converted to Motion's seconds once, `0` is an intentional instant duration, negatives clamp to zero, a non-finite value falls back to the personality default, and an explicit `durationMs` on a spring personality still selects duration-based spring timing. `ScrollReveal` never read any timing prop, so for it only the inherited type members disappear.

The compatibility promise and how it is discharged. The aliases were introduced as deprecated in 2.19.4 with the promise "compatible for one minor" (JSDoc: "legacy seconds remain compatible for one minor", "during the compatibility window"; CHANGELOG 2.19.4: "one-release legacy compatibility"). Every release since has been a 2.19.x patch, up to the current 2.19.36: no minor ever shipped between the promise and 3.0, so the window never opened and closed on a minor of its own. The 3.0 major discharges it because no consumer exists to claim it: the syntax-tree census of 2026-10-03 (JSX attributes, spread attributes, `createElement` calls, `typeof` component references and props-type references, over the package source, the showroom, app-bithire, app-evnto and app-platform) found 128 elements of the seven primitives, every one resolved to its import, and the only un-suffixed timing attributes on a design-system primitive were four test elements inside this package that existed to prove the compatibility branch. The showroom passes none. The three apps pass none: the nine spread attributes on a design-system `CountUp` in app-bithire are inline object literals carrying only `prefix`, `suffix` or `decimals`, and the `duration={steady ? 0.9 : 1.9}` in app-evnto is on that app's own local `CountUp` component, not this one. No props type of the family is referenced outside the contract and the primitives themselves.

Downstream apps: an un-suffixed timing prop on one of these primitives (or on an object typed with one of these props types) fails at compile time on upgrade. The migration is a rename with a unit decision, so it is not automatic: a value that was positive and at most 10 was seconds and must be multiplied by 1000 (`duration={0.32}` becomes `durationMs={320}`); any other value was already milliseconds and is renamed unchanged (`delay={80}` becomes `delayMs={80}`); a value computed at runtime needs the same decision made by hand. On `ScrollReveal` delete the attribute. An untyped caller that keeps passing an un-suffixed prop now gets the default timing instead of its value.

Tests. The four elements and the resolver cases that asserted the legacy acceptance are removed with the branch they proved (seconds mapping, millisecond pass-through above the window, `*Ms` precedence over an alias). In their place the focal tests assert the same rendered timings through the `*Ms` props and assert that values of ten or less are milliseconds, never seconds, for the resolver, `FadeIn`, `StaggerChildren`, `TextReveal` and `CountUp`, plus a type-level assertion that none of the four props types publishes an un-suffixed timing key.
