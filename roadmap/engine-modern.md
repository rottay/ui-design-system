# Modern Engine Premium Uplift Lane

This lane takes the `modern` engine from "hand-made, mid-tier — near-indistinguishable
from `rustic`" to the **Quiet Premium** target defined by the spec. The engine already
has every premium primitive it needs on disk (a motion catalog, a gradient/glass/glow
family, an elevation scale, focus/state tokens); it consumes a private, partial copy of
each and hardcodes the rest inline. **This is a consolidation-and-wiring program, not a
rebuild.** Each WO (a) converges a fragmented concept onto ONE foundation-layer token
contract and (b) deletes the inline residue and dead CSS it replaces.

The normative law is the spec at
`../../docs-engineering/engineering/design-system/runtime/engines/modern/README.md`
(read it FULLY before any WO — every WO below implements a numbered section of it).
The file:line evidence in each Why line comes from the audit at
`../../docs-engineering/archive/audits/2026-07-06-modern-engine-visual-audit-davila.md`.

Lane-wide rules (binding on every WO):

- Repo: `/Users/daniel/Developer/Rottay/ui-design-system`. All paths below are relative to
  the repo root unless prefixed. Engine source lives in `packages/core/src/`.

### Binding tenant-ownership supersession (2026-07-16)

This section supersedes every later historical instruction in WO-ENG-18 or WO-ENG-20 that
would register `themanagementmiami`, or any other customer tenant, as a bundled
`BrandTheme`, `TenantConfig`, `KNOWN_TENANTS` entry or production CSS file. Those passages
remain useful evidence of how the defect was discovered, but they are not executable
instructions after `@rottay/design-system@2.19.24` and `@rottay/tenancy@2.0.5`.

- **Static, versioned files own product grammar.** DS defaults and each vertical preset own
  engine, anatomy, topology, responsive task projection, semantic icon/chart/AI mapping,
  accessibility law and the vertical's baseline presentation. BitHire's code-owned baseline
  is the Folk-inspired `bithire-evidence-ledger` / Skyline People Desk posture.
- **The tenancy DB owns customer identity.** Every customer tenant, including
  `themanagementmiami`, receives its versioned, published visual override from
  `TenantThemeConfig`. A checked-in customer theme is allowed only as a one-shot migration
  seed, test fixture or regression oracle; it must not participate in runtime lookup after
  publication and must never overwrite a later app-platform edit.
- **Precedence is fixed:** `DS defaults -> static vertical preset -> published DB override ->
  preview override`. Preview is isolated to the authorized preview session and never becomes
  production authority without publish. Tenant data cannot change behavior, permissions,
  engine, topology, semantic mappings, React/code, selectors or raw CSS.
- **Host resolution is identity-only.** A hostname maps to `{ tenantId, vertical }`; it never
  selects styles, components, behavior, a separate bundle or a separate deploy. Assets are
  approved-pack/CDN references stored by ID in DB, not arbitrary executable payloads.
- **SSR owns the bytes used for hydration.** The server validates the published row, compiles
  an immutable artifact keyed at least by `{ tenantId, rowVersion, compilerVersion }` plus
  the vertical/DS baseline identity, embeds those exact bytes in SSR and hydrates from the
  same artifact. Keep an in-process L1 for hot reuse and add a shared Redis/edge L2 before
  fleet scale, with publish/rollback invalidation; the browser never reads the tenancy DB.
- **Visual freedom has no convergence quota.** BitHire and The Management deliberately use
  the same routes, components, product behavior and vertical invariants while reading as
  radically different companies. The Management's warm cream, gulf-teal, terracotta and
  editorial-type fixture is seed/regression evidence for that DB payload, not a second
  code-owned product skin.

Ordering is by leverage: the two foundation WOs first (ENG-01 mints the token canon + the
ratchet; ENG-02 makes the evidence surfaces real), then the token-contract WOs in parallel
where deps allow, then the theme.css drain once the token homes exist, then content/layout,
then the signature pass last.

### WO-ENG-19 The personality bridge inverts the documented merge chain
- **Outcome** — A tenant's explicit chrome outranks a derived personality flag. The runtime stops stamping the lowest-priority layer of the merge chain at the highest precedence CSS offers.
- **Why** — Found 2026-07-09 by the WO-GAT-03 hostile-tenant probe, which is the only gate that could have found it. `runtime/personality/primitives.ts:171-172` derives `--ds-card-border` and `--ds-card-border-hover` from the boolean `personality.card.showBorder`, and `runtime/bootstrap/SystemCssVariablesBridge.tsx` stamps every such variable INLINE on `document.documentElement`. Inline is the highest precedence in CSS, so it beats the generated tenant block — including the more specific `html[data-tenant='x'][data-theme='dark']` rule that carries the tenant's own `chrome.cardComponent.border`.
  Measured on `/probe/whitelabel-torture?fixture=torture-dark` after WO-TOK-05 landed: the generated dark block correctly declares `--ds-card-border: #4D0033` (the tenant's value), while `document.documentElement.style` carries `--ds-card-border: var(--ds-color-border-primary)` and wins. `--ds-card-bg` and `--ds-input-bg` are NOT stamped inline and therefore resolve to the tenant's values, which is why WO-TOK-05 fixed five of six channels and not the sixth.
  `CLAUDE.md` documents the chain as `DS base -> vertical baseline -> BrandTheme -> generated artifacts`. Personality is derived and belongs near the bottom. The bridge puts it on top. A boolean the tenant did not type outranks a color the tenant did.
  Same shape as the defect Fable's advisory found at `ThemeProvider.tsx:987` (a second emitter that ignores the rule the compiler follows) and the same shape as WO-ENG-05's `'none'` guard, which was fixed in one emitter and not the other. The runtime has a second styling emitter that no gate watches.
- **Depends on** — WO-TOK-05 (which proved five of the six channels are generator-side, isolating this one).
- **Steps** —
  1. Decide where personality belongs in CSS precedence and write it down once. It cannot be inline: inline is reserved for values that must beat every stylesheet, and personality is the layer everything else is allowed to override.
  2. Move `resolvePersonalityCssVariables`' output out of inline styles into a stylesheet block at the correct layer, or suppress each variable the tenant's compiled chrome already declares. Prefer the former: the latter leaves two emitters that must agree forever.
  3. Audit the FULL output of `resolvePersonalityCssVariables` for other channels a tenant can also declare — `--ds-card-border` is the one the probe caught, not necessarily the only one.
  4. The WO-GAT-03 baseline must shrink from 2 violations to 1 (`select/native/background-color`, a different defect). That is the gate.
- **Files** — `packages/core/src/runtime/personality/primitives.ts`, `packages/core/src/runtime/bootstrap/SystemCssVariablesBridge.tsx`, `packages/showroom/e2e/whitelabel/torture-baseline.json`.
- **Acceptance gate** — `test:whitelabel` green with the baseline at 1; a drill recorded (re-inline one personality var, watch the probe go red, revert); `test:gates` green with first-party baselines UNMOVED (rottay/bithire declare `showBorder` consistently with their chrome, so their pixels must not shift — if they do, that is the same bug rendering today and must be reviewed by eye); build + `pnpm test` green.
- **Do NOT** — Do not fix this by deleting `showBorder`. Do not leave the bridge stamping anything inline that a tenant may legitimately override.
- **Size** — M.

- **SCOPE EXPANSION 2026-07-09 (found mid-execution, verified)** — The inline stamp is only HALF the defect. `BrandTheme.chrome.card` (an abstract personality dial: `showBorder`, `defaultElevation`, `hoverElevation`, `hoverTint`) and `BrandTheme.chrome.cardComponent` (concrete authored chrome: `border`, `shadow`, `bgHover`) are two sibling sub-objects (`contracts/themes/index.ts:155-179`) that **terminate in the SAME six CSS variable names**: `--ds-card-border`, `--ds-card-border-hover`, `--ds-card-shadow`, `--ds-card-shadow-hover`, `--ds-card-bg-hover`, `--ds-card-hover-transform`.
  `brandThemeToPersonality()` (`compilers/brand-theme/index.ts:90-92`) bridges `chrome.card` into `PersonalityTokens.card`, and the static generator spreads `personalityVariables()` (inside `baseDeclarations`) **AFTER** `compiledBrandVars` (`generator/index.ts:645-654`). Under object-spread semantics the later key wins, so the abstract dial silently overrides explicitly authored chrome **inside the generated CSS text itself**, not only through the inline bridge. `CardPersonalityTokens`' fields are non-optional in the resolved `PersonalityTokens`, so the override likely fires by default rather than in an edge case.
  Additionally, `ThemeProvider.tsx:1012-1016` writes `appearanceVars` INLINE on the same `document.documentElement` that `SystemCssVariablesBridge` writes to. **Two inline writers on the same node**, and which one wins depends on React effect-firing order, which nothing documents or tests.
  **This WO's scope grows**: decide, and write down once, who wins between an abstract dial and an authored value for the same variable. A tenant that typed a hex should not be overruled by a boolean it also set. Then make the static and runtime paths agree, and make the two inline writers one.

### WO-ENG-22 BrandTheme.chrome is single-valued, so a two-mode tenant cannot author both
- **Outcome** — A tenant that renders in both clear and dark mode can author chrome for both. Today it authors one and the other is whatever the single set happens to look like against the opposite ground.
- **Why** — Measured 2026-07-09, on the `evnto` tenant rendered dark (its `palette.darkBackgroundColor` is `#131210`, and it paints `rgb(19,18,16)`), through the same flagship gallery every other tenant uses:
  - the Badge computes `background-color: rgb(232,232,224)` under `color: rgb(255,255,255)`. Near-white on near-white. Rec.709 luminance delta: **23.6**.
  - the native Select computes `background-color: rgb(255,255,255)` under `color: rgb(232,232,224)`. Delta: **23.6**.
  Both are unreadable, and both are visible in `test-artifacts/engine-modern/eng-18/vertical-evnto-1280.png`.
- **Root cause, read not guessed** — `BrandTheme.chrome` (`contracts/themes/`) has ONE set of values. `evntoBrandTheme.chrome` is light-authored: `chrome.controls.input.bg` is white. The generator's dark block applies that same light chrome (`darkChromeVars`, added by WO-TOK-05, deliberately, because for a light-first tenant like bithire it is correct). The rottay artifact's own spec comment states the mirror image of this problem in its own words: *"rottayBrandTheme.chrome (sidebar/layout/table/controls) is single-valued and dark-authored, so compileBrandTheme cannot also produce a light variant of it."* Two tenants, the same structural hole, noticed from opposite sides and never named.
- **This program made it visible, and partly worse.** WO-ENG-17 gave evnto the modern engine it declares (it rendered `classic` before, so nobody saw this). WO-TOK-08 then wired `--ds-color-bg-input` to `chrome.controls.input.bg` so the control surface would follow the tenant — which is right, and which routes evnto's white input chrome onto its dark ground. Before that change evnto's select fell back to the design system's dark default and was legible **by accident**. A fix that makes a tenant channel real will surface every tenant that authored that channel wrong.
- **Depends on** — none. Should land before any evnto adoption work, and before `app-evnto` takes a DS version bump: it currently renders `classic`, so this is invisible in that product today and will not be after WO-ENG-17 ships.
- **Steps** —
  1. Decide the shape. Two candidates, and this is the real decision: (a) `chrome` gains a `dark` sibling (`chrome.dark.controls`, etc.), authored per mode, falling back to the single set when absent; or (b) chrome values become mode-aware pairs the way `palette` already is (`bg` / `darkBg`). (b) matches `BrandPalette`'s existing shape and the `darkBackgroundColor` precedent; (a) is a smaller diff. Write the decision down before writing code.
  2. Author evnto's dark chrome. Author rottay's light chrome, or declare in the type that rottay is dark-only and make the light block fail closed rather than emit a dark-authored chrome onto a light ground.
  3. A contrast gate, drilled: for every first-party tenant, in every mode it declares a ground for, assert the Rec.709 luminance delta between each control's background and its own text exceeds a threshold. The pixel harness exists (`packages/showroom/e2e/visual/effects.spec.ts` decodes a screenshot into a canvas). The existing `a11y.apcaPairings` counter reads solid tokens from the compiled theme and cannot see a light chrome landing on a dark ground, which is why it reports 6 and not 8.
- **Files** — `packages/core/src/contracts/themes/index.ts`, `packages/core/src/compilers/brand-theme/index.ts`, `packages/core/src/runtime/tenant/storage/static/generator/index.ts`, `packages/core/src/tokens/ts/brand-themes/{evnto,rottay}.ts`, a new contrast spec under `packages/showroom/e2e/visual/`.
- **Acceptance gate** — the new contrast gate green for every first-party tenant in every mode it declares, with a DRILL (reintroduce evnto's white input chrome into its dark block, watch it go red); sighted captures of evnto and rottay in both modes; `test:gates` green with first-party pixels moving ONLY where a contrast defect is being corrected, and every moved baseline named in the evidence; build, `pnpm test`, and `engine-token-audit --check` green.
